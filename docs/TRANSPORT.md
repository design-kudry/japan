# Перемещения, бронирования и билеты

Срез 17.11.2026. Полная функциональная спецификация: [SERVICE_SPEC.md](SERVICE_SPEC.md), раздел 10. Макеты: [Добавить перемещение](https://www.figma.com/design/aUQnGXZkcguG0Sow8bTp1h/Untitled?node-id=321-9173).

## Модель

Trip → Booking[] → Segment[]. Booking — один заказ, Segment — одна часть пути. Пересадка вычисляется между соседними сегментами, отдельным объектом не хранится.

Booking: id, tripId, supplier, pnr, passengers, price|null, currency, sourceFile|null, segments[], createdAt, updatedAt.

Segment: id, kind, carrier, number, from/to {name, code, timeZone}, departureUtc, arrivalUtc, status, seat, travelClass, terminal, gate. Черновик использует departureLocal/arrivalLocal; для поездки без дат есть assignedDay=day-N.

## Рабочий интерфейс

- Вход из конструктора и меню настроек.
- Транспорт сначала не выбран: самолёт, автобус, поезд, паром.
- После выбора показываются способы: «По номеру рейса» только для авиа, «Загрузить билет», «Ввести вручную». Пункта «По маршруту» в UI нет.
- Gravity Card, TextInput, DatePicker, Select, Button; шапка с возвратом. Выбор транспорта — одна чёрная рамка без двойного контура.
- Кнопка конструктора — outlined xl с Car 20 px. Между ней и «Добавить место» 12 px; перед блоком действий 20 px от последней карточки.
- Поиск рейса — TextInput xl с лупой 16 px и placeholder «Номер рейса».
- Ручная форма поддерживает несколько сегментов и пересадки, общие поля заказа и файл.
- Перед записью есть просмотр и явное подтверждение. Нажатие на сегмент маршрута открывает Booking целиком.
- Есть редактирование, удаление с подтверждением и отказ от изменённого черновика с подтверждением. ID/createdAt при редактировании сохраняются.

## Валидация

Названия отправления и прибытия, даты/время, зоны и допустимый тип обязательны. Прибытие позже отправления по UTC. Каждый следующий сегмент не раньше предыдущего прибытия. Стоимость, если задана, конечная и неотрицательная; ноль разрешён. Дата отправления должна соответствовать поездке, бездатный маршрут использует назначенный день.

DST: пропущенное/неоднозначное местное время не выбирается молча. Коды и существование рейсов внешним источником не подтверждаются. Пассажиры хранятся текстом. Вычисляемые длительности не становятся отдельным источником данных. Статус unknown по умолчанию; селектор ручного статуса сейчас скрыт.

## Файл билета

Один PDF/JPEG/PNG/WebP до 20 MiB. До окончательного сохранения — только выбранный файл в состоянии формы. После сохранения — байты в IndexedDB travel-ticket-files/files, метаданные в sourceFile. Можно скачать из Booking. При замене/удалении выполняется очистка соответствующего файла; удаление всей поездки не делает каскадной очистки всех билетов.

Доступность только в текущем браузере и origin. Загрузка не означает распознавание, проверку подлинности или облачную ссылку.

## Ещё не подключено

Онлайн-поиск по номеру/маршруту, OCR/PDF extraction/BCBP, LLM, проверка существования/статуса рейса, облачное хранение и фоновые уведомления. Без серверной конфигурации кнопка поиска недоступна; есть ручной ввод.

TransportProvider — клиентский контракт будущего сервера, а не работающая интеграция с поставщиком:

| POST | Данные | Ответ |
| --- | --- | --- |
| /flights/lookup | number, date | segments |
| /journeys/search | kind, from, to, date | segments |
| /tickets/extract | multipart file | Черновик Booking/Segment |
| /segments/verify | segments | verified и сегменты |

TRANSPORT_API_BASE можно настраивать только после реализации сервера. Секреты провайдера остаются на сервере. Любой будущий автоимпорт сначала должен возвращать проверяемый черновик, а не автоматически записывать бронирование.

## Проверка

Тесты tests/transport.test.mjs покрывают время UTC/ночной прилёт, пересадку, невалидные поля/последовательность, DST, сохранение ID и нулевую цену. Это не доказательство готовности сетевых интеграций и не полная автоматизация UI CRUD.
