# Аудит Travelapp и идеи улучшений

Срез на момент PR places-map UX. Цель: зафиксировать, как сервис устроен сейчас, где болит, и что улучшать дальше.

## Вердикт

Рабочий клиентский MVP маршрута/мест/расходов на открытых данных. Сильные стороны: единый React-конструктор с картой, отказ от вымышленных данных, прозрачные источники фото. Главные риски: двойной стек (React + legacy Japan HTML), медленные и дублирующиеся сетевые запросы мест, хрупкая связка геометрии шторки JS↔CSS, отсутствие синхронизации между устройствами.

## Что работает хорошо

- Hash-роутер и localStorage дают офлайн-ядро поездки без бэкенда.
- MapLibre + Leaflet fallback закрывают большинство устройств.
- AbortController + debounce на pan/search снижают гонки.
- Прогрессивный `countryPlaces` и урезанный `placesInBounds` улучшили TTI каталога/карты.
- Карточка места честно показывает `—`, если часов/цены нет.

## Проблемы (по приоритету)

### P0 — UX / доверие

1. **Шторка конструктора** — режимы `full`/`peek` были завязаны на CSS (`visibility:hidden` контента, скрытие ручки). Свободная высота ломалась «почти у верха» и «вниз пропадал контент». Исправление: latch только у краёв, во время drag chrome = `half`, ручка в full остаётся.
2. **Скорость мест** — всё ещё зависит от Wikipedia/Photon/Overpass; нет единого in-flight кеша между вкладкой, картой и конструктором.
3. **Кириллический фильтр** — EN-only названия отбрасываются; для не-RU поездок каталог редеет.

### P1 — продукт

4. Поездки «по числу дней» нельзя позже привязать к календарю без миграции ключей `day-N`.
5. Удаление поездки не чистит `trip-expenses:*` / `travel-notes-v1:*`.
6. Меню ⋮ конструктора пустое; длительность маршрута — только пешеходная оценка ~4.5 км/ч.
7. Расходы заточены под Японию (¥, фиксированные люди в сидах).

### P2 — инженерия

8. Dual surface: React SPA vs `japan.html` + city pages; дубли DAYS/каталогов.
9. Документация частично отставала (5 Photon probes, debounce 1200ms) — сверять с `SERVICE_SPEC.md`.
10. Тесты не в npm scripts; часть ожиданий устарела относительно кода.
11. Мёртвые пропы/пути (`placesContent`, старый `SheetHandle` вне RouteExplorer).

### LLM-описания по клику (вопрос продукта)

Идея: открыл карточку → нейросеть пишет «зачем идти» + цену; результат кешируется и отдаётся другим.

Это **не херня**, но **не как первый шаг без бэкенда**:

- Сейчас всё клиентское и без ключей. Общий кеш «для других людей» = нужен сервер (или хотя бы общая БД) + биллинг модели.
- Latency: хороший текст 1–3+ с; нужен скелетон и таймаут, иначе карточка «тупит».
- Качество: галлюцинации про часы/цены опасны — модель должна опираться на факты (wiki/OSM), а не выдумывать ¥.
- Юридика: лицензии Wikipedia/CC, маркировка «сгенерировано», политика ошибок.

Практичный путь: (1) сейчас — фильтр wiki + «почему идти» по категории; (2) потом BFF: по `wikidata/placeId` генерировать 2–3 предложения из extract+tags, класть в KV-кеш; (3) показывать бейдж источника. Без общего бэкенда «сохранили у одного — увидел другой» невозможно.

## Рекомендуемый порядок работ

1. Закрепить шторку тестом/ручным чеклистом (full ↔ free ↔ peek, контент не исчезает).
2. Place cache + скелетоны → субъективная скорость мест.
3. Delete-trip cleanup + npm test.
4. Языковой фильтр мест.
5. Решение по legacy Japan HTML (оставить read-only или портировать остатки в React).

## Чеклист проверки после изменений шторки

- [ ] Потянуть почти до верха и отпустить чуть ниже — контент и ручка на месте, режим не «залипает»
- [ ] Довести до упора вверх — full, «Карта» работает, ручкой можно снова опустить
- [ ] Тянуть вниз до середины — расписание видно
- [ ] Довести до нижней полоски — peek, видна только ручка; тап поднимает
- [ ] Отпустить на произвольной высоте — остаётся там
- [ ] Выбрать место на карте — browse + мини-карточки; назад — half
